## THE ROOT CAUSE — read this first

**The installed `regent-cli.exe`/`regent-deacon.exe` at
`C:\Users\Ralph Lacanlale\AppData\Local\Programs\Regent\bin\` were dated
July 16** — 9 days stale, predating this session's fixes AND the entire
document-rendering pipeline (`__render` sidecar shipped 2026-07-18; see
`docs/handoffs` history / memory `doc-pipeline-redesign` for waves W0–W5).
Every `regent` command the user ran resolved to this stale copy via PATH.
This single fact explains most of what looked like "still broken after the
fix": the fix was real and correct in the source tree, it just never reached
the binary the user actually invoked.

**Fixed 2026-07-25**: stopped the running stale processes, copied
`target/release/regent-deacon.exe` and the freshly compiled
`dist/regent-cli.exe` over the two stale files, verified end-to-end with
`regent doctor` using only the sibling-install candidate (the real
end-user path, no dev-tree candidates nearby) — health round-trips clean.

**Likely also explains** the "document generation looks purely static"
complaint: `find_renderer()` (`regent-tools/.../create_document/renderer.rs`)
falls back to native (static) writers only when *no* renderer binary is
found at all — a stale-but-*present* `regent` on PATH would have been
picked, invoked with `__render`, and (predating that subcommand by 2 days)
failed or produced generic output, without ever reaching the graceful
fallback. Verified directly: piping a themed PPTX job into the *now-updated*
installed CLI's `__render` returns a valid, themed `.pptx` (PK-zip magic
bytes confirmed). **Not yet confirmed by the user** re-generating a real
document — flagged as Open Task #1.

**Lesson for future sessions**: after any fix, check `where regent` /
`Get-Process regent-cli,regent-deacon` and compare the installed binary's
timestamp against the source tree before declaring anything fixed. A
rebuilt-and-verified source tree means nothing if the user's shell resolves
to a different, older binary.

## OPEN TASKS

### 1. Confirm the document-generation fix with a real request (HIGH PRIORITY)
User reported PDFs/DOCX/PPTX/XLSX looking "purely static," unlike Anthropic's
per-request custom design. Five prior waves (W0–W5, see memory
`doc-pipeline-redesign`) already built dynamic per-doc theming, keyless
images, varied PPTX layouts, and DOCX/XLSX theming — all previously verified
in isolation. Strong circumstantial evidence (binary dates, direct sidecar
test) points to the stale-install root cause above as the actual reason it
*looked* unfixed. **Ask the user to generate a document now** (Desktop or
CLI) and check for real variation before assuming any new code defect. If
still static, capture the exact prompt + output and check which format
specifically regressed — start at `create_document`'s theme/deck routing in
`regent-tools/src/*/create_document/{theme,palette,deck}.rs`.

### 2. Desktop: implement a real message queue while a turn is busy
Confirmed missing (unlike the CLI, which already had this — see #`da50b0e`).
Currently pressing Enter while `busy` is a silent no-op in
`features/chat/presentation/Composer.tsx` (text/attachments preserved, but
nothing is queued or auto-sent). Design: mirror the CLI's
`enqueueIfBusy`/`dequeueOnIdle` shape as a new
`features/chat/domain/promptQueue.ts` in Desktop (parallel file, not shared
— this repo doesn't share code between CLI/Desktop, see the voice
locate/spawn triplication precedent), wire into `ChatView.tsx`, add a small
"queued" indicator near the composer. TDD as with everything else this
session.

### 3. Gateway (deacon webhook path): bounded per-conversation queue gate
`src/crates/regent-deacon/src/infra/webhook/inbound.rs` has no busy-guard at
all — a second platform message for the same `{platform}:{chat_id}` key
while a turn is running just blocks silently on `SessionManager::run_turn`'s
per-agent `tokio::sync::Mutex` (FIFO-fair, so ordering is fine, but there is
no depth cap and no user-facing "still working" feedback). The standalone
`regent-gateway` binary (Telegram-only in practice) already has this exact
pattern solved — `application/runner.rs`'s `running: Arc<Mutex<HashMap<...,
CancellationToken>>>` busy-guard with an immediate "Still working... /stop"
reply — but that's a *reject*, not a *queue*, and is intentionally left
alone (its own module doc explicitly frames "no silent queueing" as
deliberate). For the webhook path, the user wants genuine queuing: add a
small bounded per-key pending-count gate (e.g. cap 3) in
`artifacts_ops.rs`-adjacent code or a new `webhook/queue_gate.rs`; over cap,
reply immediately with a bounded "still working" message instead of piling
up blocked tasks. Real security consideration: without a cap, a burst from a
multi-user group chat (Slack/Discord/Telegram groups) has no per-conversation
resource ceiling today (the existing rate limiter is per user_id, not per
chat_id).

### 4. File editor + git commit/push panel for coding sessions
User asked for: a closed-by-default window on the main chat page for
sessions that do coding, VSCode-style file browse/edit, plus Commit / Commit
+ Push / Push buttons, all functional, **plus Ctrl/Cmd+S to save**. **Not
started — design questions still owed to the user before any code**: git
push is exactly the class of action the project's own safety rules require

(a) which directory does this operate on — the session's actual git working
tree, or just `$REGENT_HOME/artifacts`? (b) full read-write file tree, or
read + the existing diff-preview only? (c) exact push confirmation UX (a
button that itself opens a confirm dialog naming the branch/remote, most
likely, matching the artifacts `ConfirmDialog` pattern just shipped this
session). Reuse candidates once scoped: `shared/ui/ConfirmDialog.tsx`
(this session), `shared/ui/diffLines.ts` (this session, for showing
uncommitted changes), the artifacts file-tree/list pattern in
`features/artifacts/`.
