## Step 5 landed, and killed the ladder above it (`d5a587e`, 2026-07-28)

**Step 5 as written was a no-op, by arithmetic.** The block is not a selection
from the corpus — it IS the corpus (`render_prompt_block` = every `memory` +
every `user` node, uncapped; `add_entry` refuses an over-budget write rather

injects precisely the two entries already in the prompt.

canary data.** Additive→replace needs the new source to know something the old
one does not. It does not. They need a different corpus shape.

build, so memory written after it (learning loop, concurrent session, this

### How to regenerate the data

The instrumentation is committed but **off by default**. To rerun:

1. `cargo build -p regent-deacon --bin regent-deacon`
2. Copy `~/.regent/{state.db,config.yaml,.env}` to a scratch `REGENT_HOME` —
   never point this at the live home: it upgrades the DB to schema v10 and
   writes sessions.
3. Run the deacon with `REGENT_MEMORY_SHADOW=1` and drive it over **stdio
   JSON-RPC** (`session.create`, then `prompt.submit {session_id, text}`). It is
   a stdio daemon: detached with no stdin it logs "stdin closed" and exits.
4. Shadow lines land in `$REGENT_HOME/logs/` under target `memory_shadow`.

The driver and analysis scripts were in the session scratchpad and are
**deliberately uncommitted** — they carry the owner's memory node ids. Both are
~80 lines and cheaper to rewrite than to recover.

## W5 landed, and the row was wrong both ways (`4d96655`, 2026-07-28)

The plan said `.usage.json` "records use_count/view_count/state and nothing
consumes it". Source and the live library disagree on both halves:

- **Two automatic consumers exist.** `curate` every 6h (stale at 30 idle days,
  **archived at 90**) and `index_render`'s MRU ranking past 24 skills. The
  plan's own gate says automatic ranking waits for W1 attribution — **it has
  been live all along**, and it is the exposure-feedback loop W3 forbids for
  memory (off the index → not seen → not used → stays off). Latent at 13 skills
  vs a cap of 24; compounds with the 90-day archive once it crosses.
- **The telemetry is empty.** `record_use` has exactly one caller —
  `regent-agent/src/bin/repl.rs`, a dev REPL. Live library: 13 skills,
  `use_count` **0 on every one**. And **12 of 13 have no telemetry row**, which
  `curate` skips — so the pass can act on one skill in thirteen.

Shipped inside the gate: `plan_curation` (suggestion-only, whole library,
`Untracked` as a first-class outcome), and the 6-hourly pass now logs what it
cannot age. **`curate`'s scope is deliberately unchanged** — widening it to
untracked skills would archive a dozen of the owner's skills on the next pass.
That is an owner decision and is the obvious next question to put to them.

Not done on purpose: wiring `record_use` into the deacon. There `skill_view`
*is* the use event; a second counter would manufacture the signal, not find it.

### The starvation guard (`8c88b96`) — and the fix that didn't work

Owner picked the index-floor question. **The floor mechanism does not work**, so
the goal was delivered a different way.

Reserving 4 of 24 slots for the least-recently-active skills was built, refuted
and reverted. At 50 skills it shows ranks 1-20 and 47-50: the same four hold the
reserved slots forever (exposure never refreshes `last_activity_at`), 21-46
starve as before, and 21-24 *lose* visibility. It moves the boundary and charges
four slots. An earlier cut was worse — with no provenance filter every reserved
slot went to bundled skills, which can never be archived. **Caught by a test.**

What shipped instead: `plan_curation` computes the index's visible set with the
same function `render_index` uses, and a >90-day skill that is **not visible** is
reported `HiddenByIndexCap` rather than archived. No new state, no index cost.

Also from round 2 of co-review: one `list()`+`load_usage()` snapshot drives the
candidate set, the idle clock *and* visibility (it used to mix two views and pay
a second record pass every 6h); `plan_curation`/`apply_plan` split so a plan can
be reviewed before it is applied; and `apply_plan` revalidates, so a skill used
between planning and applying is not retired on a stale timestamp.

**Precisely** — the stronger wording is not earned: nothing is archived while
absent from the visible set computed *in the same snapshot*. A skill hidden for
89 of its 90 idle days then promoted by another's archival is visible when
judged. A real minimum-exposure guarantee needs `last_exposed_at` persisted
separately from `last_activity_at` (folding it in would make exposure outrank
use) — **an open owner decision**. `SkillLibrary::archive` called directly stays
unguarded, deliberately.

Latent regardless: the cap needs 24 skills, the live library holds 13.
