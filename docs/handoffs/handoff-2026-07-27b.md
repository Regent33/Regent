### How to regenerate the data

The instrumentation is committed but **off by default**. To rerun:

1. `cargo build -p regent-deacon --bin regent-deacon`
2. Copy `~/.regent/{state.db,config.yaml,.env}` to a scratch `REGENT_HOME` —
   never point this at the live home: it upgrades the DB to schema v10 and
   writes sessions.
3. Run the deacon with `REGENT_MEMORY_SHADOW=1` and drive it over **stdio
   JSON-RPC** (`session.create`, then `prompt.submit {session_id, text}`). It is
   a stdio daemon: detached with no stdin it logs "stdin closed" and exits.
4. Shadow lines land in `$REGENT_HOME/logs/` under target `memory_shadow`.

The driver and analysis scripts were in the session scratchpad and are
**deliberately uncommitted** — they carry the owner's memory node ids. Both are
~80 lines and cheaper to rewrite than to recover.

## The methodological lesson, which is the most reusable thing here

**Four claims failed when checked against source. Three were mine.**

1. *"`Retry-After` is read zero times, ever."* False — `run_with_retry`
   (`http.rs`) has always preferred it, with a test. The header never appeared in
   logs because those providers do not send it.
2. *"The failover hop cap never costs a reachable provider."* False, and my own
   test comment said so while the test name claimed safety.
3. *"Container images need scanning."* There are no Dockerfiles in the repo.
4. My first W2 fix was a **no-op**: bounding the walk to 3 providers does nothing
   when the chain *is* 3 providers each retrying 3 times internally. Only caught
   by checking `3 × chain_length` against the measured 8.4× ratio.

Every one was *read off logs or inherited from the audit, then stated as a claim
about code*. Same shape as the `429` grep artifact already in memory. **Before
acting on any bullet in the plan, verify it against source.**
