## W8 — the false-positive rate, measured instead of assumed

The module said turning hits into an FPR "needs someone to label them". Done:
the real detector over every UTF-8 file in three corpora.

| corpus | files | flagged | marker | invisible |
|---|---|---|---|---|
| this repo's `src` | 1,800 | 1.2% | 0.8% | 0.4% |
| this repo's `docs` | 123 | 3.3% | 3.3% | 0% |
| an unrelated app repo | 57,069 | 0.6% | 0.5% | 0.1% |

**Every marker hit inspected was a false positive**, and 86% came from four
phrases — `run the following command` (98, install docs), `this overrides` (89,
docstring cliché), `without any restrictions` (35, pypdf on PDF permissions),
`jailbreak` (15, the gcloud SDK's own injection-filter flags).

Read per tool result rather than per corpus, that is ~1 read in 150 — usable.
Read as a tree scan, a real hit sits in 274. Both framings are in the source.

Two fixes, each with **zero** cost to coverage:

- **`this overrides` deleted.** Proven redundant: the override rule matches its
  verb as a raw substring, so "this overrides the system prompt" is still caught
  — as `instruction override`, by the *stricter* reject-side rule.
- **A leading BOM is not evasion.** It was **refusing memory writes**: `trim`
  does not remove U+FEFF (it stopped being `White_Space`), so a note pasted from
  a BOM-prefixed file came back "invisible/control character U+FEFF not
  allowed" — the user's real memory, blocked.

**What the BOM fix does not cover, found by running it:** `read_file` returns
JSON, so the mark sits after `{"content":"`, not at offset 0, and no offset-0
strip reaches it. Rather than strip a BOM out of what the model reads for the
sake of a log line, the log now **names the codepoint** —
`invisible_char="U+FEFF"` is dismissable at a glance where `invisible_chars=true`
was not. Pinned as a stated limit, not quietly left.

## W9 — the plan's claim was four-fifths true

"Correctness parts (cancel, limits, durable results, failure propagation,
status) come free with W1." Checked against source before building:

| part | verdict |
|---|---|
| durable results | ✅ free — ledger `result` + artifacts |
| failure propagation | ✅ free — `fail`, `Completion::verdict`, `StopReason` |
| limits | ✅ free — deadline enforced by the runner's own select arm (`overdue()` has no production caller and is redundant) |
| status | ⚠️ only bolted onto the next user turn; **no way to ask** |
| cancel | ❌ **false** — `request_cancel` had no caller outside its own test |

So a 45-minute background job was **unstoppable and unlistable**. Added
`job.list` / `job.cancel` and `regent jobs [cancel <id>]`. The reply says
*requested*, not *cancelled* — it is cooperative — and the listing shows
`running (cancelling)` until the runner notices.

### The bug that was worse than missing

`interrupt_running_jobs` marked **every** running row interrupted, with no notion
of who owns it. That is only correct if one deacon can exist. It cannot: the CLI
spawns one per command, beside the long-lived one the voice server holds.

Proven, not reasoned: seed a running job, run **`regent status`** — a read-only
command — and it comes back `interrupted`. The owning process's real outcome is
then refused as stale by `finish_job`'s attempt guard, so **a job that succeeded
reports as interrupted and its result is dropped**.

Fixed with a liveness lease: `job_attempts.heartbeat_at`, renewed on the timer
each runner already had (background_task's cancel poll; a new select arm for
cron, which had none). Recovery reclaims only expired attempts — 60s, four
polls' slack. A NULL heartbeat means "written before this column" and is treated
as expired, so old rows behave exactly as before.

Three existing tests encoded the single-process assumption and now say what they
mean via `interrupt_abandoned_jobs(0.0)` / `recover_abandoned(0.0)`.

## W9's other half — shipped, after correcting myself twice

`6586667`. Two things I had reported were wrong, both caught the same way:

- **"No concurrency cap at all" was false.** I had grepped `regent-deacon` and
  `regent-tools`, not the workspace. `delegate_task` has been capped at 3
  (`DelegationConfig::max_concurrent`, enforced by `.buffered()`) since it
  shipped. `background_task` was the uncapped one — and the idempotency key
  only stops the *same* job twice, so a model emitting a batch of parallel
  calls fanned out unboundedly against one provider quota. Now 3 shared slots.
- **It refuses rather than queues**, deliberately: a `queued` job has no attempt
  row, so no lease protects it, and waiting would walk straight back into the
  recovery bug fixed the same day.

**`interrupt_subagent` was a genuine hole.** The agent checks its cancel token
only at the top of the run loop, *and* `Agent::new` minted every child a fresh
token. A synchronous `delegate_task` fan-out — 3 children, each with a
50-iteration budget — never learned the user pressed stop, and the parent
observed it only after the whole fan-out returned. `ToolContext` now carries the
turn's interrupt and `Agent::new` **adopts** one already present, so a child
built from a clone of the parent's context is linked without the delegation code
knowing tokens exist.

Checked at the boundary that this does not leak into fire-and-forget work: every
session builds its context fresh via `ToolContext::new`, so a detached
background job still mints its own and survives its parent turn being stopped.
The test fails by **panic**, not assertion, if a child reaches the model after
the stop — the fixture's provider is `unreachable!`.

## W10's gate — measured, closed, and pointed at the wrong function

`4a704a3`. The gate asked for "a measured workload crossover, not a corpus
size", so it got one (384-dim, release build, 50 queries):

| nodes | `vector_search` | | nodes | `rebuild_derived_edges` |
|---|---|---|---|---|
| 1,000 | 1.23 ms | | 500 | 122 ms |
| 10,000 | 15 ms | | 1,000 | 465 ms |
| 100,000 | 136 ms | | 2,000 | 1.78 s |
| | | | 5,000 | **11.3 s** |

**Two source claims were asserted and never checked. Both wrong.**

- `embeddings.rs`: brute-force search is "sub-millisecond" at thousands of
  nodes. At 1,000 it is 1.23 ms — off by ~1000× at the scale it named.
- `semantic.rs`: the O(n²) edge rebuild is "fine to ~5k nodes". At 5k it takes
  **11.3 seconds**, and `memory_graph()` runs it on *every* graph dump — an
  eleven-second stall opening the visualization page.

The gate stays **closed**, and the W10 row was also aimed at the wrong
function. Search is fine to ~37k nodes against a 50 ms budget and the live
corpus is **28**; the thing that actually breaks is the edge rebuild, at ~1–2k.
Running it with `k = 0` (scores every pair, writes nothing) puts **97.5%** of
the cost in the pairwise cosine rather than the DB writes — so ANN is the right
tool, for *that* function, if the corpus ever nears 1k. No code changed:
nothing is near its ceiling.
