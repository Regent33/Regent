# FATAL findings

## FATAL 1 — Hermes’s live header makes the scorer contract incorrect

Section 5 says the harness emits a frozen join template:

> `prefix`, `separator`, `suffix`

and the scorer constructs every candidate prefix from that template.

But Hermes’s prefix contains:

> `[N% - x/y chars]`

That is not a fixed prefix. At least `N` and `x` are live values. You have not frozen:

- whether `x` is based on the complete store, the selected block, or the candidate first-`k` records;
- whether the percentage and count are recomputed for every candidate `k`;
- rounding of `N`;
- formatting at digit-width transitions;
- whether Hermes emits the header at all for zero admitted entries;
- whether the header seen in the final native block is valid when transplanted onto a shorter scorer-created prefix.

This matters directly at every token boundary. It is not cured by calling it a 152-character header, because **it is not necessarily 152 characters for every candidate prefix**.

It also creates a logical mismatch:

1. The product renders one block with one live counter.
2. The scorer synthesizes many shorter candidate blocks.
3. Those synthetic blocks may contain a header the product would never have emitted for those contents.

### Correct repair

Do not ask the scorer to reconstruct native rendering from a static template.

For each query and each prefix length `k = 0…n`, the harness should emit the **exact opaque native block that the product renderer produces for the first `k` selected records**. The scorer should only tokenize those complete strings and select the first non-fitting `k`.

At minimum, the harness artifact should contain:

- `k`;
- ordered IDs represented in that block;
- exact rendered bytes/string;
- exact product renderer/version;
- an assertion that the block corresponds to exactly the first `k` IDs and no others.

If invoking the native renderer for every `k` is impossible, you must freeze and test a complete renderer function, including the live counter algorithm. A static `prefix/separator/suffix` is insufficient.

This also removes the BPE additivity problem without requiring the scorer to imitate either renderer.

## FATAL 2 — Regent’s `<provenance>` is an unfrozen per-entry experimental input

The native Regent entry is:

```text
- [memory | <provenance> | trust 0.5] "<record text>"
```

But `<provenance>` is not specified anywhere in the protocol or corpus definition.

That means a harness author has had to choose, or inherit through an unstated API path:

- the provenance value;
- whether it is constant or entry-specific;
- whether it includes corpus IDs, filenames, paths, namespaces, or UUIDs;
- whether it varies by seed;
- whether it is escaped or normalized;
- whether its length is correlated with insertion order or record identity.

Because that string is charged once per result, this choice can materially change `target_delivery@600`. It can also make different seeds have different rendering costs for reasons unrelated to selection.

This is exactly a still-open harness decision affecting the primary score.

### Correct repair

Freeze the exact provenance construction and input. Prefer one of:

1. **Constant provenance for every record**, with its exact literal value frozen; or
2. The exact product-required provenance generated by one named public insertion API, with all inputs to that API frozen and the resulting provenance strings committed in the corpus artifact.

Then assert:

- provenance is identical across systems/seeds where intended;
- or, if entry-specific, the complete `id -> provenance` mapping is frozen;
- no temporary path, machine name, random UUID, timestamp, or seed-dependent value appears;
- the harness-rendered string exactly equals the production retrieval renderer’s output.

Until this is fixed, the native Regent token cost is not uniquely determined by the protocol.

## FATAL 3 — `mrr` is contradictory for Hermes

Section 4.2 defines:

> Reciprocal rank of the target in the full ranking.

Section 5 says each harness emits:

> the ordered list of entry ids it would deliver

Hermes therefore has an order. It is query-independent, but it is still an order in which the target has a well-defined position.

Yet §6.3 says:

> Hermes is N/A on ranking quality.

And §7 says:

> Ranking quality cross-system is impossible.

Those statements cannot all hold.

A static ordering has a perfectly computable reciprocal target position. It is not evidence of a query-conditioned ranking operation, but mathematically it is an MRR over the delivered order. A scorer author must currently choose between:

- calculating Hermes MRR under §4.2; or
- emitting N/A under §6.3.

That is a direct scoring ambiguity.

### Correct repair

Choose one and state it consistently. The better choice is:

- Compute **target reciprocal position** for both products.
- Describe Hermes’s value as the MRR of its **query-independent delivery order**, not as retrieval-ranking quality.
- Reserve “query-conditioned ranking quality” for Regent and query-conditioned baselines.

Alternatively, rename Regent’s metric to something explicitly operation-specific and mark Hermes N/A, but then §4.2 must no longer define MRR over every harness’s full order.

## FATAL 4 — The protocol assumes an exhaustive Regent ranking without specifying how one is obtained

The assertions require:

> every stored id exactly once in a full ranking

But Regent’s described retrieval architecture uses bounded seed lanes and graph expansion. The protocol does not state:

- the exact retrieval method called;
- all recall/top-`k`/candidate-limit arguments;
- whether the public API can return all 500 records;
- whether “not retrieved” records are appended;
- if appended, in what order;
- whether the raised character budgets affect retrieval candidate limits or only rendering/storage.

A bounded retrieval result is not an exhaustive ranking. A harness must not manufacture a tail silently, because at larger budgets that synthetic tail can turn retrieval misses into deliveries.

The assertion may simply abort rather than produce ambiguity, but the measurement still is not executable unless the product actually exposes the required exhaustive order.

### Correct repair

Freeze the exact retrieval API and its arguments. Then choose one of these semantics:

### Preferred: finite product result

Treat Regent’s returned list as the product’s complete candidate output:

- no harness completion;
- missing target gives delivery `0`;
- missing target gives reciprocal rank `0`;
- IDs in the returned list must be unique and valid;
- remove the assertion that every stored ID must appear.

This measures what the product actually supplies.

### Alternative: exhaustive rank

Only call it an exhaustive ranking if Regent has a public API that genuinely ranks all 500 records. Freeze that API and assert it returns all 500 without harness completion.

Do **not** append omitted records unless a specific tail-completion rule is preregistered and results using the synthetic tail are separately labelled.

## FATAL-B3 — Static oracle 11 is not operationally specified

# The native-rendering issue: formatting contest or honest estimand?

## Native rendering is honest for your stated product estimand

Your estimand is:

> the memory context each product actually supplies, given the same number of rendered tokens

Under that estimand, native wrappers count. If Regent spends tokens on provenance and trust metadata, those tokens are unavailable for records. If Hermes spends a fixed amount on a header, those tokens are also unavailable.

So **do not strip native formatting from the primary metric** merely because it hurts Regent. Stripping it would change the estimand after discovering an unfavorable product behavior.

But your current native rendering has to be proven to be the rendering actually supplied to the downstream model—not a debug display, diagnostic serializer, or harness-only presentation. `render_recall` must be the actual production context construction path.

## Add a standardized-rendering decomposition

Native delivery alone cannot tell whether a difference came from:

- selection/ranking;
- record order;
- fixed header cost;
- per-entry metadata;
- target record length.

You should therefore report:

1. **Primary: native-rendered `target_delivery@B`**  
   Product capability, including formatting overhead.

2. **Secondary: standardized payload rendering**  
   Same product-produced order, but raw record text under one shared renderer.

3. **MRR / reciprocal target position**  
   Budget- and renderer-independent.

4. **Formatting diagnostics**
   - fixed header tokens;
   - metadata tokens per entry;
   - raw payload tokens admitted;
   - wrapper-to-payload token ratio;
   - delivery difference between native and standardized rendering.

Do not make native and standardized versions two interchangeable primaries. Keep native as preregistered primary and label standardized rendering as the decomposition/sensitivity analysis.

# Stratum D

## It is lexically disjoint only in a narrow sense

Your assertion supports this narrow statement:

> No query template token exactly overlaps a status-marker token.

That is true and useful.

But this sentence is false:

> A system must carry the mapping semantically or lose the currency signal.

It can use the dates instead.

For every shown tuple:

- gold: `2026-06`
- rejected: `2025-11`
- superseded: `2024-03`

Queries say:

- presently;
- today;
- as of now;
- at this moment.

A system can identify the most recent same-entity/same-relation record without understanding `ACTIVE`, `IN EFFECT`, or `STANDING` at all. Because entity and relation are strong lexical filters, a simple system can:

1. find the three same-entity/same-relation records;
2. choose the largest date.

That solves the intended currency distinction.

The fixed role-date correlation also leaks the marker ontology globally: every gold marker co-occurs with the newest date, every superseded marker with the oldest date, and every rejected marker with the middle date.

### Consequence

D is not purely a synonym-mapping test. It is a test where the exact status-token shortcut is removed but date recency remains available.

That does not invalidate D, but it invalidates the stated interpretation.

### Required repair

Either:

- narrow the claim to **removal of exact status-token overlap**, and add a deterministic **entity/relation + latest-date** baseline; or
- if you specifically want to test status semantics, remove date as a solution—for example, equalize dates, make dates nonmonotonic with status, or provide a query-specific cutoff under which “latest date” is not equivalent to status.

The first repair is less invasive and more honest.

## A frozen thesaurus can solve D

Yes. A frozen ontology mapping:

```text
presently/today/now/moment
    -> ACTIVE / IN EFFECT / STANDING
```

can solve the status part.

That does not mean D tests nothing about memory. Retrieval systems routinely depend on semantic equivalence between query vocabulary and record vocabulary. But it tests **semantic/schema-aware retrieval over an explicit status vocabulary**, not temporal reasoning or general memory capability.

Add the frozen thesaurus/ontology baseline. If Regent cannot beat it, that is informative.

# Intervention corpus

- none of its three designated negatives retains the original slot-match pattern;

- the number of records matching both entity and relation decreases by the intended amount;

# Other tightenings

## `target_too_long` is currently tested against the wrong quantity

You define it as:

> the target’s own rendered text exceeds B, so no ranking could have delivered it

Mandatory prefix, suffix, and wrapper overhead also matter. A target may be shorter than B by itself but impossible to deliver even when ranked first because:

```text
prefix + rendered target + suffix > B
```

Define `target_too_long` as:

> the exact native block containing only that target, rendered in first position, exceeds B.

This becomes especially important for Regent’s wrapper.

## “Maximal prefix” and “first non-fitting prefix” should not be treated as synonyms

Whole-string BPE token counts are not formally additive, and Hermes’s changing header makes the candidate strings not even simple extensions of one another. It is theoretically possible for token counts not to be strictly monotonic.

Freeze the operational rule as:

> Evaluate `k = 0,1,2,…` in order and stop at the first `k` whose exact rendered block exceeds B; admit `k-1`.

Call this the **sequential complete-entry prefix**, not a mathematical maximum over all `k`, unless you separately assert token-count monotonicity for every generated sequence.

## Freeze empty-result rendering

Specify whether `k=0` means:

- empty string; or
- header-only native block.

Use what the actual product sends downstream.

## Standardized baselines versus native products

The baseline `target_delivery@600` uses a shared renderer while the product headline uses native rendering. That is acceptable, but values must not be placed in one table as if they differ only in ranking.

Clearly separate:

- native product delivery;
- standardized-order delivery;
- standardized baseline delivery.
